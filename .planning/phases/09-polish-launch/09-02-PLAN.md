  <action>
Two strategies currently exist for missing Strapi images:
- **Filter-out**: Homepage transforms return `null` and filter — items with no image are excluded
- **Placeholder**: Creative/Production use hardcoded placeholder paths like `/images/creative/service-placeholder.jpg`

Standardize on the **filter-out** approach:
1. In `app/lib/transformers.ts` (shared transformers from 09-01), ensure `transformWorkflow`, `transformPortfolio`, `transformTestimonials`, and `transformKeyProjects` all return `null` for items where the primary image is missing, then filter nulls from the result array
2. Check page-specific transformers that remain in individual page files (e.g., `transformCreativeServices`, `transformEventProjects`, `transformProductionServices`, `transformClientLogos`). Apply the same filter-out pattern
3. Remove any hardcoded placeholder image paths (e.g., `/images/creative/service-placeholder.jpg`) — these images likely don't exist and would show broken images anyway

The pattern to follow (from Homepage):
```
return items.map(item => {
  const imageUrl = getStrapiImageUrl(item.image);
  if (!imageUrl) return null;
  return { ...props, image: imageUrl };
}).filter(Boolean);
```

Exception: For transformers where the image is optional and the item still makes sense without it (e.g., testimonials without avatar, workflow steps without icon), keep the item but set image to `null` — don't filter out the whole item. Only filter when the image IS the content (gallery items, portfolio items, project cards).

<task type="auto">
  <name>Task 2: Add proper translation types for About and Contact pages</name>
  <files>app/[locale]/about/page.tsx, app/[locale]/contact/page.tsx</files>
  <action>
The About page has ~18 `as` type assertions to access nested translation keys. The Contact page has 2. These are unsafe — if translation structure changes, they silently return undefined.

The root cause: `getTranslations()` returns `Translations` (typed as `typeof enTranslations`), which should already have the full nested structure. The `as` casts suggest the type inference isn't reaching deep enough, or the pages are accessing keys that don't match the inferred type.

Fix approach:
1. First, read the actual EN and VI translation JSON files to understand the real structure for ABOUT_US and CONTACT_US keys
2. In the About page, replace the pattern:
   ```
   const aboutTranslations = (t as { ABOUT_US?: Record<string, unknown> }).ABOUT_US || {};
   ```
   with direct access:
   ```
   const aboutTranslations = t.ABOUT_US;
   ```
   If TypeScript complains, the issue is that ABOUT_US doesn't exist on the Translations type — which means the translation JSON is missing those keys or the type isn't being inferred correctly. In that case, add the missing keys to the EN translation JSON and update accordingly.
3. Remove all `as` casts in both About and Contact pages. Access translations directly using the typed `t` object (e.g., `t.ABOUT_US.INTRO.LABEL`)
4. If any translation keys genuinely don't exist in the JSON, add them with appropriate EN/VI values
5. Use optional chaining (`?.`) with nullish coalescing (`??`) for safety, but NOT `as` casts

Do NOT create a separate types file for translations — the type is already inferred from the JSON import.
  </action>
  <verify>`npx biome check app/[locale]/about/page.tsx app/[locale]/contact/page.tsx` passes. Grep for ` as {` in about/page.tsx and contact/page.tsx returns zero results. `npm run build` succeeds.</verify>
  <done>About page has zero `as` type assertions for translation access. Contact page has zero `as` type assertions. All translation access is directly typed through the Translations type. Build passes with no TypeScript errors.</done>
</task>
